# Dock fresh-view integration map (R6)

## Verdict and evidence boundary

Use a stable, presentation-independent context per dockable and let its typed `App.axaml` data template construct a new view. Keep shared project/selection/edit state and mutations in `MainWindowViewModel`; move control-specific event routing into the corresponding view; move any mutable editor draft that must outlive a view out of that view. Do not wrap or return a live control as another template result.

This is a design seam, **not a production fix claim**. V3 proved only that its simplified template could construct fresh Topology/Properties equivalents around the existing VM, retain a ParameterPane draft, and move a placeholder Links view using the real Dock factory. It did not exercise production Topology handlers, physical gestures, the real Links layout, or Avalonia's old-layout-queue path (`analysis/dock-fresh-view-v3.md:7-26`). D6 reproduced the wrong-`LayoutManager` failure with the real Links pane before and after its rejected direct-control template (`C:\Users\julia\AppData\Local\Temp\opencode\etsfix-d6\RESULT.md:10-18`). V1 confirms real native pointer reachability of the Topology/Properties duplicate-parent failures, but its document redock evidence is limited to one document/center-drop and observed empty visible hosts (`analysis/review-native-docking.md:13-28,44-46`).

### Exact closure references to remove

- Topology view handlers must stop capturing `MainWindow` fields/methods: `TopologyTree`, `OnCatalogForNode`, `OnTreeSelectionChanged`, `OnTreeDoubleTapped`, `OnTreePointerPressed`, `OnTreePointerMoved`, `OnTreeDragOver`, `OnTreeDrop`, `ResetDrag`, `TargetOf`, `OwnerLineOf`, `NodeOf`, `NodeAt` (`MainWindow.axaml.cs:670-775`). Preserve event ordering and target semantics rather than replacing native drag/drop with a VM-only operation.
- Properties `StartRename` and `OnNameKeyDown` currently capture the window's named `NameBox` and VM (`MainWindow.axaml.cs:364-381`). The shared `OnKeyDown` also calls window-level operations (`:324-362`); only pane-local focus/apply behavior should move.
- Current `SyncDevicePanes`, `ReloadPanes`, and `RefreshFromCatalog` coordinate pane instances (`MainWindow.axaml.cs:899-926`). A view split must retain these update triggers or move the subscriptions to the stable pane state; do not leave subscriptions attached to a discarded view.

## Migration order and independent work

1. **Topology + Properties foundation:** add typed, control-free pane contexts and fresh `TopologyPane` / `PropertiesPane` views; preserve the current `MainWindowViewModel` as shared model/edit state. Move their view-specific handlers and make DataContext explicit. These two can be implemented/tested together without changing `ParameterPane` or `GroupLinksPane` internals, but share `App.axaml`'s document/tool template boundary, so they are not independent template edits.
2. **Parameter draft owner:** can be extracted/tested independently before fresh-view wiring (no Topology/Properties control overlap). Do not switch the Parameters template until its lifecycle owner supports multiple disposable views and existing close/open/new/undo semantics remain covered.
3. **GroupLinks state/template and explicit-move track:** its per-view state extraction can be prepared separately, but the template/move validation shares the same app template and docking manager. Keep the production explicit-move defect as an open gate; test the actual nested pane, not a placeholder. Do not fold a speculative Avalonia source/package workaround into the application refactor.

Thus **only the Topology/Properties pane implementation is a single, clean first migration**. Parameter draft ownership is separately extractable; GroupLinks needs its own layout-manager investigation. The three fresh-view migrations should not overlap edits to the same template file in parallel.

## Regression contract for implementation

Use an isolated synthetic project/settings/catalogue. For Topology and Properties separately, use actual native pointer input (`SetCursorPos` + `SendInput` or equivalent OS input) against the running application: float by dragging the real tool header, then redock by dragging the real floating tab/pane to its home target. No `Factory.FloatDockable`, `MoveDockable`, raised Avalonia pointer events, or factory-only result may count as this gate. Repeat float → redock at least three times in one process and assert after each transition:

- no exception/process exit; one visible main host after redock, no ghost/empty visible HostWindow, dockable owner is its original home dock;
- current visual is rooted exactly once in the expected host, and each newly presented view is fresh (no reuse of the prior control identity); the shared context/state identity remains stable;
- Topology selection remains the actual selected `TreeNode`/model selection, updates Properties and device panes, and works both while floated and after redock. Exercise context-menu click-target selection and every tree action. Perform an actual native device drag/drop to another line/segment and verify the model/undo state;
- Properties edits apply to the selected device/group address, preserve blank-name rejection and DPT behavior, Enter applies, and F2 focuses/selects the Properties editor in the floating host and again after redock;
- floated Ctrl+Z/Y reaches project undo/redo once; text-editor Ctrl+Z remains local and does not also mutate project state. Verify no duplicate subscriptions after repeated view disposal/recreation.

For Parameters, dirty two different device drafts, switch selection, create/recreate views across float/redock, and prove drafts, validation messages, Apply, Discard, project replacement/undo invalidation and close prompts match the current contracts. Extend `tests/Knx.ParameterUi.Tests` (including `--native`) and `tests/Knx.Shell.Tests`; the existing `tests/Knx.Docking.Tests` covers real HostWindow + factory float/X and keyboard routing, but not native pointer input or fresh Topology/Properties views.

For Links, separately use the production `GroupLinksPane` nested layout: float it, explicitly native-drop it into the Parameters document dock, then return/redock; repeat and verify owner/root/layout rendering and link edits. Capture stale-layout evidence if it fails. A passing placeholder or absence of an exception with blank/detached content is not green.

Build/regression baseline: `dotnet build ets6.sln -v minimal` passed on this checkout (0 errors, 5 existing warnings). Required post-change build remains that command; run `dotnet run --project tests/Knx.ParameterUi.Tests`, `dotnet run --project tests/Knx.ParameterUi.Tests -- --native`, `dotnet run --project tests/Knx.Docking.Tests`, and `dotnet run --project tests/Knx.Shell.Tests`, plus the native-pointer scenarios above.
